# Architecture 문서

`architecture.md`는 plan을 읽기 전에 DB 구조 변경, 코드 흐름 변경, 주요 처리 순서를 한눈에 파악하기 위한 문서다.

## 위치

`.codex/plan/architecture.md`

## 작성 목적

| 목적 | 설명 |
|------|------|
| 전체 그림 선확인 | plan.md의 세부 설계를 읽기 전에 변경 방향을 먼저 이해한다 |
| 흐름 가시화 | DB 변경, API 처리, 코드 호출 순서를 단계별로 연결한다 |
| 변경 차이 표시 | 기존 흐름과 변경 후 흐름의 차이를 직관적으로 드러낸다 |
| 구현 연결 | 각 흐름이 plan.md TaskList와 checklist.md 실행 순서로 이어지게 한다 |

## 기본 구조

```markdown
# Architecture

## 전체 변경 요약

- 변경 대상:
- 핵심 흐름:
- 주요 의존성:

## 변경 전 흐름

1. 상위 단계
   1-1. 하위 단계
   1-2. 하위 단계

2. 다음 상위 단계
   2-1. 하위 단계

## 변경 후 흐름

1. 상위 단계
   1-1. 하위 단계
   1-2. 하위 단계

2. 다음 상위 단계
   2-1. 하위 단계

## DB 구조 변경

1. 테이블/엔티티 변경
   1-1. 컬럼 추가/수정/삭제
   1-2. 관계 변경
   1-3. 인덱스/제약 조건 변경

2. 마이그레이션 영향
   2-1. 기존 데이터 보정
   2-2. 롤백 시 고려사항

## 코드 흐름 변경

1. 진입점
   1-1. Controller/Route/Component
   1-2. 요청/이벤트 입력값

2. 처리 흐름
   2-1. Service/Hook/State 변경
   2-2. Repository/API 호출 변경
   2-3. 응답/상태 업데이트 변경

3. 검증 흐름
   3-1. 테스트 대상
   3-2. 수동 확인 경로

## plan.md 연결

| Architecture 단계 | plan.md 연결 | checklist.md 연결 |
|-------------------|--------------|-------------------|
| 1. ... | 설계 결정 또는 Task | 체크 항목 |
```

## 번호와 들여쓰기 규칙

| 규칙 | 예시 |
|------|------|
| 상위 단계는 `1.`, `2.`, `3.` 형식으로 쓴다 | `1. 주문 생성 흐름 변경` |
| 하위 단계는 `1-1.`, `1-2.` 형식으로 쓴다 | `1-1. 주문 요청 DTO에 필드 추가` |
| 하위 단계는 상위 단계 아래에 들여쓴다 | 상위 단계 다음 줄에 공백 3칸 이상 |
| 상위 단계 사이에는 빈 줄을 둔다 | `1.` 블록과 `2.` 블록을 분리 |
| 단계 하나에는 변경 행동 하나만 담는다 | `컬럼 추가`, `조회 조건 변경`을 분리 |

## 작성 기준

- plan.md보다 먼저 읽어도 변경의 큰 흐름을 이해할 수 있게 쓴다.
- DB 구조 변경과 코드 흐름 변경이 서로 어떤 순서로 이어지는지 드러낸다.
- 변경 전 흐름과 변경 후 흐름을 함께 적어 차이를 비교 가능하게 한다.
- 구현 세부 코드는 plan.md에 두고 architecture.md에는 흐름과 의존 관계를 남긴다.
- 흐름이 없는 단순 변경이면 `전체 변경 요약`과 `코드 흐름 변경`만 짧게 작성한다.

## 리뷰 기준

| 관점 | 확인 질문 |
|------|----------|
| 가독성 | 번호, 줄바꿈, 들여쓰기로 흐름이 직관적으로 보이는가 |
| 완결성 | DB, 코드, 검증 흐름 중 필요한 항목이 빠지지 않았는가 |
| 정합성 | architecture.md의 흐름이 plan.md TaskList와 충돌하지 않는가 |
| 의존성 | DB 변경 후 코드 변경처럼 선후 관계가 명확한가 |
| 과밀도 | plan.md에 있어야 할 구현 세부 코드가 과하게 들어가지 않았는가 |
