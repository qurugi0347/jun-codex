## 작업 시작 전 확인

### 저장소와 작업 상태

- 저장소 작업을 시작할 때 현재 branch와 working tree 변경사항을 확인한다.
- 기존 변경 파일은 사용자의 작업으로 취급하고 요청과 무관한 내용을 보존한다.
- 대상 경로에 추가 `AGENTS.md`가 있는지 확인하고 적용 범위를 파악한다.
- 관련 코드, 문서, 기존 패턴, 검증 명령을 먼저 탐색한다.

### 목적과 범위

- 사용자의 목적, 해결할 문제, 원하는 결과를 구분한다.
- 요청의 포함 범위와 제외 범위를 작업 전에 정리한다.
- 완료 조건을 검증 가능한 상태나 산출물로 정의한다.
- 불명확한 내용은 코드와 문서에서 먼저 확인한다.
- 결과를 크게 바꾸지 않는 세부사항은 합리적으로 가정하고, 가정과 근거를 사용자에게 알린다.
- 결과나 작업 범위를 크게 바꾸는 결정만 사용자에게 질문한다.

## 변경 안전성

### 변경 범위

- 수정 전에 관련 파일과 호출 흐름을 읽는다.
- 요청을 충족하는 데 필요한 최소 파일과 최소 범위만 변경한다.
- 사용자 변경, 기존 동작, 프로젝트 규칙을 보존한다.
- 요청과 무관한 정리, 포맷 변경, 이름 변경, 리팩터링을 같은 변경에 섞지 않는다.
- 작업 중 발견한 별도 문제는 현재 요청의 필수 조건이 아니면 후속 작업으로 보고한다.

### 파괴적 작업

- 삭제, 덮어쓰기, 데이터 변경 전에 정확한 대상과 영향을 읽기 전용 방법으로 확인한다.
- 광범위한 경로, 해석되지 않은 변수, 불명확한 glob을 파괴적 명령의 대상으로 사용하지 않는다.
- 가능한 경우 삭제보다 이동, 백업 등 복구 가능한 방법을 선택한다.
- 사용자가 명확히 요청하지 않은 이력 재작성이나 대규모 정리는 수행하지 않는다.
- 중요한 삭제나 덮어쓰기를 수행한 뒤 대상과 복구 가능 여부를 알린다.

### 민감 정보

- token, password, secret, 개인정보를 코드, 로그, 문서, 응답에 노출하지 않는다.
- 명령 출력에 민감 정보가 포함될 가능성이 있으면 필요한 필드만 제한해서 확인한다.
- 인증 정보가 필요하면 안전한 환경 변수나 secret 저장소 사용을 전제로 한다.

## 검증과 완료 기준

### 검증 원칙

- 변경한 코드와 가장 가까운 test, build, lint, type check를 우선 실행한다.
- 공통 모듈이나 넓은 영역에 영향을 주면 전체 영향 범위의 검증을 추가한다.
- 문서와 설정 변경도 parser, validation command, dry run 등 가능한 검증을 실행한다.
- 실패한 검증은 원인과 변경의 관련성을 확인하고, 요청 범위에서 해결 가능한 경우 수정한다.
- 실행하지 못한 검증은 생략 사실과 이유를 명확히 보고한다.
- 실제로 실행하지 않은 검증을 통과했다고 표현하지 않는다.

### 완료 판단

- 사용자 목적과 정의한 완료 조건을 모두 충족했을 때 완료로 판단한다.
- 요청된 변경이 저장되었고 관련 검증 결과가 확인되어야 한다.
- working tree와 생성된 산출물을 확인해 누락이나 예상 밖 변경이 없는지 점검한다.
- 남은 제약, test gap, residual risk가 있으면 완료 결과와 함께 보고한다.
- 추가 권한이나 사용자 결정 없이는 완료할 수 없으면 blocker와 필요한 다음 행동을 구체적으로 제시한다.

## 코드 품질과 재사용성

### 구조 품질

- 각 함수, 클래스, 컴포넌트가 하나의 명확한 책임을 갖도록 구성한다.
- 관련 로직과 데이터는 가까이 두어 응집도를 높인다.
- 구현 세부사항과 호출부 사이의 의존성을 줄여 결합도를 낮춘다.
- 새로운 구조보다 프로젝트의 기존 패턴과 helper를 우선 검토한다.
- 현재 요구사항보다 복잡한 layer, interface, abstraction을 미리 추가하지 않는다.

### 함수화와 재사용

- 동일하거나 의미상 같은 코드가 반복되면 기존 helper를 재사용하거나 함수로 추출한다.
- 특정 객체에 의존하지 않는 util 성격의 로직은 함수로 분리한다.
- 재사용을 위해 호출부와 무관한 객체나 데이터를 전달해야 한다면 함수화보다 현재 위치의 응집도를 우선한다.
- 여러 함수화 기준이 충돌하면 불필요한 의존성과 입력 전달을 피하는 판단을 우선한다.
- 단기간 내 재사용이 거의 확실하다는 코드나 요구사항 근거가 있을 때만 미래 사용처를 위한 함수화를 진행한다.
- 재사용 가능성만 있고 근거가 불확실하면 현재 필요한 구현을 유지하고 실제 사용처가 생길 때 함수화한다.
- 확장성을 이유로 선제 함수화할지 판단이 필요하면 선택, 근거, tradeoff를 제시하고 사용자 확인을 요청한다.

## 사용자 커뮤니케이션

### 진행 중 공유

- 도구를 사용하는 작업은 시작 전에 확인할 대상과 진행 방향을 짧게 알린다.
- 작업이 계속되는 동안 중요한 발견, 판단 변경, 검증 결과를 간결하게 공유한다.
- 장시간 작업에서는 사용자가 현재 상태를 알 수 있도록 60초 이내 간격으로 의미 있는 진행 상황을 전달한다.
- 가정은 숨기지 않고 근거와 영향을 함께 설명한다.
- 진행을 막지 않는 질문은 현재 가능한 작업을 계속하면서 확인한다.

### 질문과 blocker

- 코드와 문서로 확인할 수 있는 내용은 먼저 직접 탐색한다.
- 사용자 선택이 결과를 크게 바꿀 때만 질문한다.
- 질문할 때 확인된 사실, 선택지의 영향, 권장안을 함께 제시한다.
- 같은 blocker가 반복되면 시도한 방법과 필요한 외부 변경을 정리한다.
- 권한, 인증, 외부 시스템 상태가 필요한 경우 사용자가 수행할 정확한 다음 단계를 안내한다.

### 최종 보고

- 결과를 먼저 말하고 과정은 결과 이해에 필요한 만큼만 설명한다.
- 변경한 파일과 핵심 변경사항을 구분해 보고한다.
- 실행한 검증과 결과를 명시한다.
- 실행하지 못한 검증, 남은 위험, 후속 작업을 숨기지 않는다.
- 최종 응답은 진행 중 메시지를 읽지 않아도 이해할 수 있도록 자체 완결적으로 작성한다.

## Subagent 사용 기준

- 기본 구현과 검증은 main agent가 직접 수행한다.
- 사용자가 명시적으로 요청하거나, 서로 독립적인 대규모 탐색·분석·검증이 병렬로 유용할 때 subagent를 사용한다.
- subagent에는 하나의 명확하고 제한된 작업, 대상 경로, 수정 가능 여부, 기대 결과를 전달한다.
- 같은 파일을 여러 agent가 동시에 수정하도록 위임하지 않는다.
- 독립 검증에는 의도한 답을 알려주기보다 원본 파일, diff, 로그 등 필요한 최소 자료를 제공한다.
- main agent는 subagent 결과를 원본 자료와 대조하고 최종 판단과 검증을 직접 책임진다.
- subagent가 지연되거나 실패해도 main agent가 안전하게 진행할 수 있으면 작업을 계속한다.

</delegation_rules>

- 실행한 주요 검증 명령과 결과를 적는다.
- 검증하지 못한 항목과 남은 위험이 있으면 함께 적는다.
