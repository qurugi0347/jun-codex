# Director

프로젝트 스펙을 구조화하고 변경 간 충돌을 검토한다.

## 권장 스펙 구조

```text
.codex/context/project/
├── INDEX.md
├── features/
│   ├── INDEX.md
│   ├── auth.md
│   └── payment.md
├── rules/
│   ├── business-rules.md
│   └── constraints.md
└── models/
    └── data-model.md
```

## 기능 스펙 템플릿

```markdown
# [기능명]

## 개요
기능의 목적과 범위를 2-3문장으로 작성한다.

## 비즈니스 규칙
| # | 규칙 | 조건 | 결과 |
|---|------|------|------|
| 1 | ... | ... | ... |

## 데이터 모델
| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| id | string | Y | 고유 식별자 |

## UX 플로우
1. 사용자가 ...
2. 시스템이 ...

## 기술 제약
- 제약 사항

## 의존성
- 다른 기능/모듈과의 관계
```

## 정합성 검증

| 축 | 검증 질문 |
|----|----------|
| 기능 범위 | 기존 기능과 겹치거나 모순되는가? |
| 비즈니스 규칙 | 기존 규칙과 충돌하는 조건이 있는가? |
| 데이터 모델 | 기존 모델과 호환되는가? |
| UX 플로우 | 기존 사용자 흐름과 일관되는가? |
| 기술 제약 | 아키텍처와 기술 스택 제약을 지키는가? |

## 충돌 유형

| 유형 | 의미 |
|------|------|
| 직접 모순 | 두 규칙이 명시적으로 상반됨 |
| 의존성 파괴 | 변경이 다른 기능의 전제를 깨뜨림 |
| 암묵적 충돌 | 전제 변경으로 기존 동작이 깨질 수 있음 |
| 데이터 불일치 | 같은 데이터를 문서마다 다르게 정의 |

## 심각도

| 심각도 | 의미 | 조치 |
|--------|------|------|
| `BLOCK` | 구현 불가한 논리적 모순 | 해결 후 진행 |
| `WARN` | 잠재 문제 또는 결정 필요 | 사용자 확인 후 진행 |
| `INFO` | 영향이 작지만 기록 필요 | 기록하고 진행 |
