# TaskPrReviewApplyPlan

PR 리뷰 내용을 구현 전에 검토하고 `.codex/plan/pr-review-apply-plan.md`에 적용 계획을 작성할 때 사용한다.

## 사용 예시

- `$TaskPrReviewApplyPlan PR 리뷰 코멘트 반영 계획 작성해줘`
- `$TaskPrReviewApplyPlan 리뷰 내용 중 적용할 것과 보류할 것을 판단해줘`
- `$TaskPrReviewApplyPlan gh pr review 내용을 보고 수정 방향을 계획해줘`

## 실행 절차

### 1. 리뷰 자료 수집

가능한 자료를 먼저 확인한다.

| 자료 | 목적 |
|------|------|
| 사용자 입력 리뷰 내용 | 반영 대상 원문 확인 |
| GitHub PR review/comment | PR에 남은 line comment, review summary 확인 |
| `.codex/plan/plan.md` | 기존 설계, 범위, TaskList 확인 |
| `.codex/plan/context.md` | 사용자 요청 원문, 배경, 결정 근거 확인 |
| `.codex/plan/checklist.md` | 완료/미완료 작업과 실행 순서 확인 |
| `git diff main...HEAD` 또는 현재 diff | 리뷰 대상 구현 상태 확인 |

GitHub CLI와 인증이 가능하면 아래 정보를 참고한다.

```bash
gh pr view --json number,title,url,body,reviewDecision
gh pr view --json reviews,comments
gh pr diff
```

GitHub CLI를 사용할 수 없거나 PR context가 없으면 사용자 입력 리뷰와 로컬 diff를 기준으로 진행한다.

### 2. 요구사항과 설계 방향 확인

리뷰를 적용하기 전에 아래 기준을 정리한다.

- 원래 작업 목적과 사용자 flow
- plan에서 정한 설계 결정과 tradeoff
- 현재 구현이 의도적으로 선택한 방식인지, 단순 누락인지
- 리뷰 내용이 실제 문제를 지적하는지, 선호도/스타일 차이인지
- 적용 시 변경 범위, 위험도, 테스트 영향

불명확한 부분은 코드와 문서에서 먼저 확인하고, 그래도 판단할 수 없으면 `확인 질문`으로 남긴다.

### 3. 리뷰별 적용 판단

각 리뷰 항목을 아래 중 하나로 분류한다.

| 분류 | 의미 |
|------|------|
| 적용 | 리뷰 내용이 목적/설계와 맞고 수정이 필요함 |
| 조정 적용 | 리뷰 취지는 맞지만 제안 방식보다 더 나은 수정 방향이 있음 |
| 미적용 | 리뷰가 현재 설계 방향과 맞지 않거나 적용 이득보다 비용/위험이 큼 |
| 보류 | 판단에 필요한 정보가 부족하거나 별도 작업/PR이 적절함 |
| 질문 | 리뷰 의도나 요구사항 확인이 먼저 필요함 |

미적용 또는 조정 적용 판단에는 반드시 이유와 대안을 적는다.

### 4. Apply Plan 문서 작성

`.codex/plan/pr-review-apply-plan.md`를 작성한다.

기존 파일이 있다면 아래 기준으로 처리한다.

| 상황 | 처리 |
|------|------|
| 현재 PR/리뷰와 무관한 이전 계획 | 새 계획으로 교체 |
| 현재 리뷰 반영에 도움이 되는 계획 | 유지하되 최신 리뷰와 diff 기준으로 보강 |
| 파일 없음 | 새로 작성 |

### 5. 문서 형식

`pr-review-apply-plan.md`는 아래 형식을 사용한다.

```markdown
# PR Review Apply Plan

## 목적

- 원래 작업 목적:
- 리뷰 반영 목표:
- 적용 원칙:

## 검토 자료

| 자료 | 확인 내용 |
|------|----------|
| <파일/PR/명령> | <확인한 내용> |

## 리뷰 반영 계획

| # | 리뷰 출처 | 리뷰 요지 | 판단 | 수정/대응 방향 | 이유 |
|---|----------|----------|------|----------------|------|
| 1 | <파일:라인 또는 reviewer> | <요지> | 적용/조정 적용/미적용/보류/질문 | <어떤 부분을 어떻게 수정할지 또는 대응할지> | <판단 근거> |

## 상세 수정 계획

### 1. <리뷰 요지>

- 판단: 적용/조정 적용/미적용/보류/질문
- 대상 파일:
- 현재 상태:
- 수정 방향:
- 설계 정합성:
- 더 나은 방향 또는 미적용 이유:
- 검증 방법:
- 의존성/주의사항:

## 실행 순서

- [ ] <수정 task>
- [ ] <검증 task>
- [ ] <리뷰어에게 설명할 내용 정리>

## 확인 질문

- <필요한 경우에만 작성>
```

### 6. 수정 방향 작성 기준

- "어떤 부분을 어떻게 수정할지"를 파일/함수/flow 단위로 구체화한다.
- 리뷰 제안을 그대로 따르지 않을 경우, 왜 그대로 적용하지 않는지와 대체 방향을 명확히 적는다.
- 전체 설계 방향과 충돌하는 리뷰는 `미적용` 또는 `조정 적용`으로 두고, 기존 설계의 근거와 tradeoff를 함께 적는다.
- 더 단순하거나 유지보수성이 좋은 대안이 있으면 리뷰 원안 대신 그 방향을 계획한다.
- 리뷰 반영이 별도 PR에 더 적절하면 `보류`로 분류하고 분리 이유와 후속 작업 조건을 적는다.
- 테스트 변경이 필요하면 검증 방법은 적되, 별도 TestCode PR 원칙이 있는 기존 plan과 충돌하지 않게 범위를 분리한다.

### 7. 사용자 확인

계획 요약을 제시하고 승인을 요청한다. 사용자가 리뷰 반영 구현을 요청하기 전에는 코드 변경을 시작하지 않는다.
