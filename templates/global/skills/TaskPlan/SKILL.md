# TaskPlan

사용자 요청을 구현 가능한 작업 계획으로 바꾸고 `.codex/plan/` 하위에 계획 문서 4종을 작성할 때 사용한다.

## 사용 예시

- `$TaskPlan 결제 완료 후 주문 저장 기능 구현 계획 작성해줘`
- `$TaskPlan 기존 Claude command 내용을 Codex skill로 옮기는 계획 작성해줘`

## 실행 절차

### 1. 기존 Plan 처리

기존 `.codex/plan/` 파일이 있다면 아래 기준으로 처리한다.

| 상황 | 처리 |
|------|------|
| 현재 요청과 무관한 이전 plan | 새 계획으로 교체 |
| 현재 요청에 도움이 되는 plan | 내용 활용 후 보강 |
| plan 없음 | 새로 작성 |

### 2. 요구사항 명확화

아래 3가지를 `context.md`에 기록한다.

- 목적: 이 작업을 왜 하는가?
- 문제: 어떤 문제를 해결하는가?
- 방법: 어떻게 해결할 것인가?

불명확한 부분은 코드와 문서에서 먼저 확인하고, 그래도 결정할 수 없으면 사용자에게 질문한다.

### 3. Context 수집

- `rg`, `rg --files`, `git log`, 기존 문서 등을 우선 사용한다.
- 관련 파일 위치, 기존 패턴, 테스트 방식, 배포/설정 영향 여부를 확인한다.
- 탐색한 파일과 결정 근거를 `context.md`에 남긴다.

### 4. Plan 문서 4종 작성

| 파일 | 역할 |
|------|------|
| `.codex/plan/architecture.md` | plan.md를 읽기 전 변경 목적, 전후 흐름, 핵심 선택, 작업 순서를 빠르게 판단하는 overview |
| `.codex/plan/plan.md` | 전체 설계, 범위, 설계 결정, TaskList |
| `.codex/plan/context.md` | 사용자 요청 원문, 배경, 탐색한 코드, 결정 사항 |
| `.codex/plan/checklist.md` | Phase별, Task별 실행 체크리스트 |

`plan.md`의 frontmatter status는 처음에 `draft`로 둔다.

### 5. Architecture Overview 작성

`architecture.md`는 상세 설계의 축약본이 아니라, 계획 검토자가 먼저 읽고 무엇을 왜 어떤 방식으로 진행하는지 판단하는 문서다. `문제 → 기존 흐름 → 변경점 → 선택 기준` 순서로 작성한다.

- 첫 부분에 변경의 영향과 핵심 결론을 한 줄로 쓴다.
- 변경 전·후 흐름을 비교해 무엇이 달라지는지 드러낸다. 기존 흐름이 없으면 `신규`로 표시한다.
- 구현 세부사항은 `plan.md`에 두고, architecture에는 변경 경계·의존성·처리 순서만 남긴다.
- 각 선택은 적용 조건과 tradeoff를 함께 적어 검토자가 빠르게 수용 여부를 판단하게 한다.
- DB/API/FE 중 해당하는 흐름만 작성하며, 단순 변경은 요약·선택·작업 연결만 짧게 작성한다.

`architecture.md` 작성 형식:

```markdown
# Architecture

## 한 줄 요약

<무엇이 왜 바뀌며, 어떤 선택을 하는가>

## 왜 이 변경을 하는가

- 문제와 영향: <현재 문제와 사용자·운영·코드에 미치는 영향>
- 판단 기준: <이번 작업에서 우선하는 기준>

## 변경 한눈에 보기

| 관점 | 이전 | 이후 | 해야 할 판단 |
|------|------|------|--------------|
| <흐름/데이터/책임> | <기존 또는 신규> | <변경 후> | <선택 기준> |

## 어떻게 진행하는가

1. <진입점 또는 선행 변경>
   1-1. <처리 또는 데이터 변경>
   1-2. <다음 의존 단계>

2. <검증 또는 후속 단계>

## 핵심 선택

| 선택 대상 | 선택 | 적용 조건·이유 | 대안 | Tradeoff |
|-----------|------|----------------|------|----------|
| <결정> | <채택안> | <언제/왜> | <미채택안> | <감수할 제약> |

## 작업 연결

| Architecture 단계 | 변경 대상 | plan.md Task | checklist.md 검증 |
|-------------------|-----------|--------------|-------------------|
| <단계> | <파일·DB·API·UI> | <Task> | <검증> |
```

### 6. 설계 결정 작성

중요한 결정마다 아래 항목을 포함한다.

- 선택
- 이유
- 차선책
- 차선책 미채택 이유
- tradeoff

### 7. 재사용 및 함수화 결정

반복 코드와 util 성격의 로직은 아래 기준으로 함수화 여부를 판단하고 `plan.md`의 설계 결정에 기록한다.

| 판단 | 기준 |
|------|------|
| 지금 함수화 | 동일하거나 의미상 같은 코드가 반복되거나, 특정 객체에 의존하지 않는 util 성격의 기능인 경우 |
| 현재 위치에 유지 | 재사용하려면 호출부와 무관한 객체나 데이터를 넘겨야 해 결합도와 인터페이스 비용이 커지는 경우 |
| 필요 시점까지 보류 | 확장 가능성만 있고 단기간 내 재사용이 거의 확실하다는 코드·요구사항 근거가 없는 경우 |

- 여러 기준이 동시에 적용되면 불필요한 객체나 데이터 전달을 피하는 `현재 위치에 유지` 판단을 우선한다.
- 함수화 결정마다 대상, 예상 재사용 지점, 전달해야 할 입력, 결합도, 선택 이유를 적는다.
- 단기간 내 재사용이 거의 확실한 경우에만 미래 재사용을 위한 함수화를 계획한다.
- 함수화를 보류하면 실제 중복이나 두 번째 사용처가 생겼을 때 다시 판단한다는 조건을 적는다.
- 확장성을 이유로 한 함수화 여부는 권장안과 tradeoff를 제시하고 계획 승인 시 사용자 확인을 요청한다.

### 8. TaskList 작성

- 독립적으로 실행 가능한 단위로 나눈다.
- 각 task에 변경 대상, 검증 방법, 의존성을 적는다.
- 해당 없는 DB/API/FE 섹션은 생략한다.

### 9. 사용자 확인

계획 요약을 제시하고 승인을 요청한다. 사용자가 구현을 요청하기 전에는 코드 변경을 시작하지 않는다.
